# Подготовка доступа Sber QR.API

Реализован отдельный серверный адаптер QR.API: создание счёта, формирование QR
из полученной банковской ссылки и проверка статуса с денежными операциями.
По умолчанию он выключен. Сохранение ключей на Render само по себе не включает
интеграцию и не подтверждает доступ банка. Рабочее подключение, тариф и
сценарии оплаты целиком требуют отдельной банковской проверки.

## Названия настроек на Render

В Dashboard сервиса `photo-boss` откройте Environment и добавьте отдельные строки.
Реальные значения вводятся только в закрытые поля Render.

| Key | Какое значение сохранить |
| --- | --- |
| `SBER_QR_CLIENT_ID` | ClientID приложения, выданный порталом Sber API |
| `SBER_QR_CLIENT_SECRET` | ClientSecret того же приложения |
| `SBER_QR_CERT_PASSWORD` | Пароль клиентского сертификата, заданный при его выпуске |
| `SBER_QR_CERT_FILE` | `/etc/secrets/sber-qr-client.p12.b64` — файл с Base64 исходного зашифрованного сертификата `.p12` |
| `SBER_QR_CERT_FORMAT` | `p12-base64` — единственный поддерживаемый формат, также используется по умолчанию |
| `SBER_QR_CA_FILE` | Необязательный путь к PEM-набору доверенных CA для сервера банка; дополняет системные корни |
| `SBER_QR_MEMBER_ID` | Номер участника/организации, выданный Сбером для QR.API |
| `SBER_QR_ID_QR` | Идентификатор QR/торговой точки, выданный Сбером |
| `SBER_QR_TID` | Идентификатор терминала, выданный Сбером |
| `SBER_QR_API_BASE_URL` | Адрес API, подтверждённый банком для выбранной среды; тестовый адрес не подставляется автоматически |
| `SBER_QR_TOKEN_URL` | Адрес получения токена, подтверждённый банком для выбранной среды |
| `SBER_QR_ENDPOINTS_CONFIRMED` | Пока `0`; `1` допускается после проверки адресов именно этого продукта у банка |
| `SBER_QR_SUCCESS_CODE` | Подтверждённый банком код успешного ответа QR.API |
| `SBER_QR_OPERATION_SUCCESS_CODE` | Подтверждённый банком код успешной денежной операции |
| `SBER_QR_ENV` | `sandbox` для тестовой подписки; рабочий вариант — `production` |
| `SBER_QR_ENABLED` | Пока `0`; `1` разрешает новые счета только при полной конфигурации, но не заменяет банковскую приёмку |

ClientSecret и пароль сертификата — разные значения. Логин и пароль входа в
СберБизнес сюда не нужны. Ключи QR.API нельзя подставлять в
`SBER_MERCHANT_LOGIN`/`SBER_MERCHANT_PASSWORD`: эти имена используются имеющимся
модулем интернет-эквайринга с платёжной страницей банка.

При подготовке доступа можно сохранить строки через **Save only**. Это сохранит
настройки без запуска новой публикации. Не выбирайте `production` для тестовых
ключей. Не включайте рабочий приём до проверки отдельного рабочего доступа.

## Сертификат и проверка готовности

Трёх значений ClientID, ClientSecret и пароля недостаточно. Для последующих
серверных запросов потребуется клиентский сертификат, выпущенный порталом Сбера,
и проверка сертификата самого банковского сервера. Бинарный файл `.p12` нельзя
вставлять как обычный текст в Render Secret File. Для подготовленного загрузчика
используется следующий контракт:

1. Исходный `.p12` остаётся зашифрованным паролем, выбранным при выпуске.
2. Base64 этого зашифрованного файла сохраняется в закрытом Render Secret File
   с именем `sber-qr-client.p12.b64`. Его содержимое не передаётся в чат и не
   сохраняется в репозитории. Base64 меняет способ представления байтов и не
   добавляет шифрования.
3. На сервере файл доступен по пути `/etc/secrets/sber-qr-client.p12.b64`.
   Пароль хранится отдельно в `SBER_QR_CERT_PASSWORD`.

`build_sber_qr_ssl_context()` из `app/sber_qr_certificates.py` читает только обычный
файл размером до 1 МиБ, принимает Base64 с переносами строк и расшифровывает
PKCS12 внутри процесса. Он проверяет наличие пары ключ–сертификат, соответствие
открытых ключей, срок действия и назначение клиентской аутентификации, если оно
указано в сертификате. Файлы без парольной защиты, неверный пароль, повреждённые
данные и неподдерживаемый формат приводят к отказу. Требование пароля не является
доказательством шифрования каждой приватной части контейнера: на вход нужен
исходный зашифрованный файл банка, отдельной проверки алгоритмов всех PKCS12-блоков
загрузчик не выполняет.

Для загрузки ключа в Python SSL используются кратковременные файлы в каталоге
с правами `0700`, сами файлы имеют права `0600`. Временный ключ дополнительно
зашифрован одноразовым случайным паролем и удаляется вместе с каталогом сразу
после загрузки TLS-контекста, в том числе при ошибке. Загрузчик не гарантирует
принудительное обнуление памяти Python/OpenSSL.

TLS-контекст всегда проверяет сертификат и имя банковского сервера, использует
системные доверенные корни и TLS не ниже 1.2. При необходимости
`SBER_QR_CA_FILE` добавляет отдельно доверенный набор CA, сохраняя системные
корни; он также читается только из обычного файла с лимитом 1 МиБ. Цепочка из
клиентского PKCS12 отправляется как цепочка клиента, но не
добавляется в доверенные корни сервера. Отключения проверки TLS нет.

`SberQRConfig.configuration_status()` возвращает только сведения о наличии
настроек и доступности непустого файла сертификата. Поле
`configuration_complete` не означает, что сертификат корректен, доступ выдан
банком или платежи работают. Отдельный загрузчик проверяет локальный сертификат
и создаёт TLS-контекст. `qr_client_issues()` дополнительно проверяет настройки
авторизации и, для заказов, идентификаторы точки/терминала и коды ответа.
Тестовая среда без подтверждённых адресов заблокирована. Пустые идентификаторы
и коды не заменяются примерными значениями из документации.

Содержимое ключей, пароля и файла не попадает в строковое представление
конфигурации или статуса. Проверка сообщает имена отсутствующих настроек без их
значений. Сам объект конфигурации нельзя передавать в `dataclasses.asdict()`,
JSON или журналы: для диагностики используется только отдельный результат
`configuration_status()`. Сам модуль не читает и не изменяет настройки старого
эквайринга.

## Запись и продажа в приложении

Когда банковский приём настроен, в формах записи и продажи по умолчанию выбран
QR Сбера. Сотрудник может выбрать уже внесённый платёж с чеком; при записи также
доступна предоплата позже. Открытие формы или изменение суммы не создаёт счёт.

После сохранения записи с положительной предоплатой очередь дожидается её
подтверждения сервером, затем создаёт один QR и показывает его в форме. Сама
запись сохраняется независимо от времени оплаты. При продаже сначала
сохраняются черновик и выбранные исходные файлы на устройстве, затем выставляется
счёт на остаток с учётом подтверждённого аванса. Количество и цена закрепляются
за счётом. Передача фотографий и завершение продажи продолжаются после
подтверждения рабочего платежа. Если подтверждённый аванс покрывает всю покупку,
сервер возвращает отдельное подтверждение нулевого остатка без создания счёта.

Номер банковского счёта и исходные параметры сохраняются в локальной очереди
перед следующей проверкой. Обрыв связи, перезапуск страницы или повторная
синхронизация используют тот же ключ; неопределённый результат не создаёт второй
счёт. Тестовый, отклонённый или возвращённый платёж не освобождает фотографии
для завершения продажи. Исходные файлы остаются на устройстве до подтверждения
передачи сервером; очищать данные браузера до этого нельзя.

В разделе рабочих операций владельцу доступна кнопка «Проверить подключение
Сбера». Она получает актуальное состояние настроек и при готовности авторизации
проверяет сертификат и OAuth. Такая проверка не выставляет счёт гостю и не
подтверждает оплату.

## Банковская приёмка перед включением

1. Проверить доступ банка к нужному продукту. Тестовая подписка не подтверждает
   активацию рабочего тарифа.
2. Получить и проверить у банка адреса нужной среды, идентификаторы и значения
   кодов успешного ответа. Затем проверить авторизацию и запросы адаптера
   именно с выданным доступом.
3. Проверить в банковской тестовой среде предоплату, покупку, повтор после
   потери ответа, отказ и возврат. Синтетические проверки приложения не
   подтверждают действующий доступ банка.
4. Подключить отдельные рабочие параметры и выполнить банковскую приёмку:
   реальная предоплата, продажа с учётом аванса и сверка выписки. Только затем
   включать приём для сотрудников.

## Серверные границы подтверждения

Счёт сохраняет провайдера (`sber_ecom` или `sber_qr`), среду и для QR.API привязку
к приложению и торговой точке в закрытом снимке. Старые счета без такого признака
сверяются прежним эквайрингом, даже если для новых счетов выбран QR.API.
Неопределённый результат регистрации не вызывает повторного создания заказа:
сохраняется прежний счёт и запрашивается его статус по номеру партнёра.

Денежное поступление появляется только при проверенном банковском статусе,
совпадении идентификатора, суммы и валюты и подтверждённых операциях оплаты.
Предоплата учитывается прежним механизмом один раз. `TEST_PAID` никогда не
создаёт рабочую квитанцию. Возвраты корректируют существующее поступление,
повторный ответ не дублирует его.

Для владельца добавлены `GET /api/miniapp/bank-payments/connection` и
`POST /api/miniapp/bank-payments/connection/check` с пустым телом `{}`.
GET показывает только конфигурацию без банковских запросов и чтения содержимого
сертификата. POST проверяет сертификат и OAuth, не создаёт заказа и не включает
приём платежей. Даже успешный OAuth не означает готовность оплаты; ответ явно
содержит `ordersCreated=false` и `paymentsVerified=false`. Доступ проверяется
повторно по действующей роли владельца в базе, а произвольные адреса/параметры
в запросе запрещены.
