# Photo-boss — проект Telegram-бота для фотосервиса

Python 3.12, aiogram 3.31, SQLAlchemy 2, PostgreSQL 16.

## Состояние

Работают создание записей через бота, загрузка фотографий по съёмкам, продажи,
чеки бронирования и оплаты с подтверждением поступлений владельцем.
Для тестов используются искусственные записи в отдельной тестовой базе.

Работают: вход владельца, назначение нескольких ролей, списки сотрудников/отелей/пакетов,
создание, увольнение и восстановление сотрудников, удаление отдельных ролей,
создание отелей/пакетов, просмотр существующих записей и съёмок,
последовательная смена статуса собственной съёмки, регистрация продажи по существующей записи,
статистика, начало смены с геолокацией и фотографией в полный рост, автоматический штраф
500 ₽ при отметке после 09:00, просмотр зарплатных записей, настройки процентов, аудит.

Обучение доступно всем сотрудникам, включая владельца. На день выбирается одна категория,
бот сразу показывает пять эталонных фотографий и принимает пять повторов по порядку.
Категория блокируется до проверки владельцем; владелец принимает 5/5 или возвращает
конкретный кадр на пересъёмку. После одобрения новый набор открывается на следующий день.


## Академия фотографа

В главном меню сотрудников появился раздел **📚 Академия**. Он объединяет:

- личный профиль фотографа: уровень, баллы, съёмки, средний чек, рейтинг качества;
- короткие уроки перед сменой: позирование, свет, цвет, работа с клиентом;
- существующую практику по 5 эталонным кадрам;
- раздел «Мои ошибки» с рекомендациями по реальным рабочим кадрам;
- достижения и уровни: Новичок → Средний → Профессионал → Мастер Photo Boss;
- библиотеку лучших работ из учебных референсов;
- отчёт прогресса за 30 дней с качеством, ошибками и продажами;
- очередь реальных рабочих кадров для разбора владельцем/администратором.

Разбор сохраняется в базе и сразу отправляется фотографу. Повторная оценка того же рабочего кадра обновляет предыдущий разбор, а не создаёт дубликат.

## Перед запуском

Если токен был опубликован в GitHub, перевыпустите его через BotFather.
Не возвращайте действующий `.env` в Git. В репозитории должен оставаться только пустой `.env.example`.
В этой ветке старый `.env` уже удалён из отслеживаемых файлов.
Для запуска создайте локальный `.env` по `.env.example`; не добавляйте его в Git.
Удаление файла из ветки не удаляет старый секрет из истории Git, поэтому раскрытый токен нужно отозвать.

1. Сохраните старый `.env` локально, если он есть. Создайте новый по `.env.example`.
2. Заполните отдельными строками `BOT_TOKEN`, `ADMIN_TELEGRAM_IDS`, `POSTGRES_PASSWORD`.
   `ADMIN_TELEGRAM_IDS` — ваш числовой Telegram ID; несколько ID разделяются запятыми.
3. Не публикуйте значения в GitHub. Compose использует `POSTGRES_*`, а внутри контейнера
   адресом базы служит `postgres`. Пароли со специальными символами обрабатывает SQLAlchemy URL.
   При редактировании `.env` учитывайте правила quoting Compose; для нового пароля удобно
   использовать длинную случайную строку из латинских букв и цифр.
4. Выполните:

```bash
docker compose config --quiet
docker compose up -d --build --wait
docker compose ps
docker compose logs --tail=100 bot
```

Проверьте `postgres: healthy`, `bot: healthy`, отсутствие перезапусков и ответ на `/start`.
Бот сначала ждёт PostgreSQL, создаёт/обновляет схему, проверяет соединение с Telegram,
и только после этого отмечает контейнер здоровым. Логи Docker ограничены по размеру.
Владелец определяется по `ADMIN_TELEGRAM_IDS`. Новый пользователь получает доступ только
после назначения роли администратором. Назначать ADMIN и изменять OWNER/ADMIN может владелец.
`/cancel` прерывает текущий ввод, `/start` обновляет меню, `/myid` показывает Telegram ID.

Порт базы на сервере не публикуется. Данные сохраняются в прежнем volume `hotel_photo_pg`.
Сохраняйте прежнее имя Compose-проекта при обновлении, иначе Docker может выбрать другой volume.
Для остановки с сохранением данных используйте `docker compose down` без `-v`.
Запускайте один экземпляр бота: память FSM и блокировки событий локальны для процесса.

## Если база уже существует

При запуске бот безопасно и повторяемо меняет старый `users.tg_id INTEGER` на `BIGINT`.
Перед первым запуском обновления всё равно рекомендуется сделать резервную копию:

```bash
docker compose stop bot
docker compose exec -T postgres sh -c 'pg_dump -U "$POSTGRES_USER" "$POSTGRES_DB"' > backup-before-patch.sql
docker compose up -d --build bot
```

Проверьте успешное завершение резервного копирования перед миграцией.
Изменение `POSTGRES_PASSWORD` в `.env` не меняет пароль роли в существующем volume:
пароль нужно согласовать с действующей базой отдельно. Не удаляйте volume ради смены пароля.
Для новой базы миграция не нужна: тип BIGINT создаётся сразу.

## Комиссия

Продажа хранит отдельно автора (`created_by_id`) и получателя (`credited_user_id`).
Получатель должен быть активным сотрудником с выбранной ролью MANAGER или PHOTOGRAPHER.
Ставка фотографа зависит от общего числа сделанных кадров **в одной съёмке**:
менее 150 — 10%, **150 и больше — 15%** от суммы продаж этой съёмки.
Количество купленных кадров и кадры других съёмок, даже за тот же день,
на ставку не влияют. Например, сделано 150 кадров, куплено 2 по 400 ₽:
продажа 800 ₽, комиссия фотографа 120 ₽.

Бот учитывает сделанные кадры по всем фотографиям, загруженным в эту съёмку.
Перед продажей фотограф загружает полный набор и завершает загрузку.
Ставка видна в карточке съёмки, после загрузки и при сохранении продажи.
При следующей продаже ставка также обновляет предыдущие продажи того же
фотографа по этой съёмке, если количество учтённых кадров изменилось.

Для менеджера приоритет ставки: персональный `Compensation` → настройка БД → `.env`.
Цена берётся из пакета записи. `PHOTO_PRICE` задаёт цену начального базового пакета
при его первом создании; существующие пакеты автоматически не переоцениваются.

`/set MANAGER_PERCENT 15` меняет процент для новых продаж менеджера без персональной ставки.
Настройка `PHOTOGRAPHER_PERCENT` и персональный процент не переопределяют правило 10%/15%.
Денежные результаты округляются до копеек, но поля БД ещё имеют тип Float.
Продажа остаётся UNPAID до подтверждения поступления владельцем; частично покрытая
продажа получает PARTIAL, полностью покрытая — PAID. Чеки не создают выплат сотрудникам.
Штраф за опоздание записывается в `PayrollEntry` как удержание −500 ₽.
Автоматические выплаты сотрудникам не реализованы.

## Чеки брони и оплаты

При создании записи с ненулевой бронью бот запрашивает фото чека. Запись сохраняется,
но менеджер не может подтвердить бронирование без приложенного чека (ожидающего проверки
или принятого). Нулевая бронь не требует чека. Это подтверждение расписания, не денег.
После регистрации продажи появляется кнопка «📷 Чек оплаты съёмки».
Вернуться к загрузке после отмены или перезапуска можно через «🧾 Чеки и оплата» → номер записи.
Одна загрузка — одно фото JPEG из Telegram до 8 МБ; PDF и альбомы не нужны.
Одновременно ожидает проверки один чек каждого назначения на запись.

Только владелец видит очередь «🔎 Проверить чеки», открывает фото и результат анализа,
сверяет операцию с банковской выпиской, вводит фактически поступившую сумму и отдельно
нажимает «Деньги поступили». Администратор и остальные сотрудники не могут подтвердить
или отклонить платёж. Каждое решение и автор сохраняются в аудите.
Отклонённый чек не учитывается, можно приложить другой. Кнопки повторного подтверждения
не создают второе поступление. Подтверждённая бронь засчитывается один раз в оплату всей
съёмки, а не каждой продажи: например, бронь 200 ₽ и продажа 800 ₽ → остаток 600 ₽.
Частичная оплата поддерживается; превышение оплаты сохраняется как покрытие следующих
продаж этой записи. Суммы поступлений хранятся в Numeric(14, 2).

Распознавание подключается переменной `OPENAI_API_KEY` в **Render → Environment**.
Не отправляйте ключ в чат и не сохраняйте его в Git. Опциональная переменная
`RECEIPT_ANALYSIS_MODEL` по умолчанию равна `gpt-4.1-mini`.
Используются [изображения в Responses API](https://developers.openai.com/api/docs/guides/images-vision)
и [Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs).
Без ключа, при отказе API, нечитаемом фото или таймауте чек остаётся в очереди ручной
проверки. После подключения/восстановления распознавания владелец может нажать
«Повторить распознавание»; это также восстанавливает анализ, прерванный перезапуском.

Модель извлекает сумму, валюту, дату, банк, получателя, номер операции и видимые замечания.
Бот сравнивает сумму с ожидаемой, отмечает старую/будущую дату, неизвестную валюту и
нечитаемые поля. Повторы проверяются по Telegram file_unique_id, SHA-256 скачанного фото
и распознанному номеру операции вместе с названием банка. Непрочитанный номер, другой
вариант названия банка, обрезка или пересжатие изображения ограничивают поиск повторов.
Повторно принять уже учтённый идентификатор операции или изображение нельзя; уникальные
ограничения базы защищают также от одновременного подтверждения копий.

**Анализ изображения не доказывает подлинность чека и поступление денег.** Получатель
и операция обязательно сверяются владельцем. Проверки через банк, ОФД/ФНС и подписи
платёжного провайдера не подключены; автоматического подтверждения от модели нет.
Фото обрабатывается OpenAI только при настроенном ключе, с `store: false`; ссылка с
Telegram-токеном не передаётся. В БД сохраняются Telegram file_id и распознанные поля;
полные изображения остаются в Telegram. Не сохраняются тело ответа API, фото или ключи
в логах. Чеки видны владельцу, загрузка и сводка оплаты — сотрудникам своей записи.
Новую таблицу `receipts` создаёт обычный `init_db` при запуске без удаления существующих данных.

## Локальный запуск без Docker

Нужен отдельно запущенный PostgreSQL. Укажите доступные с компьютера `POSTGRES_HOST`,
`POSTGRES_PORT`, `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD` либо полный
`DATABASE_URL=postgresql+asyncpg://...` с корректным URL-кодированием.
Compose намеренно использует собственный сервис PostgreSQL и переопределяет DATABASE_URL.

```bash
python3.12 -m venv .venv
. .venv/bin/activate
python -m pip install -r requirements.txt
python -m pip check
python -m app.main
```

## Тесты

```bash
python -m pip install -r requirements-dev.txt
python -m pytest -q tests
```

Регрессионные проверки используют отдельную SQLite in-memory базу и не отправляют сообщения
реальным людям. GitHub Actions дополнительно собирает Docker-образ, запускает PostgreSQL 16
и имитацию Telegram API, проверяет здоровье бота и требует нулевое число перезапусков.


## Render

Для Render предусмотрен отдельный entrypoint:

```bash
python -m app.render_main
```

Он одновременно запускает HTTP health endpoint на `PORT` и Telegram polling.
Для сервиса нужны переменные `BOT_TOKEN`, `ADMIN_TELEGRAM_IDS` и
`DATABASE_URL` в формате `postgresql+asyncpg://...`. Репозиторий не хранит
рабочие токены или пароли.

## Автоматизация и рост продаж

- Бот отправляет менеджеру и назначенному фотографу напоминания за 24 часа и
  за 2 часа до съёмки. В сообщении есть комната, клиент и телефон для связи.
- Владелец видит «📈 KPI бизнеса» за 30 дней: записи, отказы, конверсию,
  продажи, средний чек и подтверждённые поступления.
- «🧠 Умное назначение» ранжирует фотографов по загрузке на выбранный день,
  привязке к отелю и среднему рейтингу Академии. Решение подтверждает человек.
- Через семь дней после завершённой съёмки создаётся лид «🔁 Повторные продажи»
  с готовым текстом предложения и телефоном клиента. Менеджер отмечает результат.
- «🏦 Сверка банка» связывает принятый чек с уникальной операцией банковской
  выписки и показывает несовпадение суммы. Реальный банковский API подключается
  через отдельный провайдер; без него работает безопасная ручная сверка.
- Владелец может скачать «💾 Резервную копию». Дополнительно бот отправляет
  ежедневную JSON-копию в 03:00 по `TRAINING_TIMEZONE`. Секреты и изображения
  чеков в копию не входят.
- Ошибка фонового процесса записывается в логи и отправляется владельцу;
  следующая попытка выполняется автоматически.

Для устойчивого состояния FSM задайте `REDIS_URL`. На Render используйте
внутренний адрес Key Value и закройте внешний доступ. Если переменная не задана,
бот сохраняет совместимость и использует память одного процесса.
